- `phpunit.xml.dist` defines one `drupal_mcp` suite over all of `tests/src`, so the documented full-suite command includes 10 unit classes, 5 kernel classes, and 1 functional class; no Functional JavaScript test directory exists.
- PHPUnit is configured with `failOnRisky="true"` and `failOnWarning="true"`, so risky tests and warnings must be reported as suite failures rather than passes.
- `tests/bootstrap.php` requires Drupal core’s test bootstrap and autoloader; `DRUPAL_ROOT` must point to an installed Drupal web root unless the module is located at the expected `web/modules/custom/drupal_mcp` depth.
- The bootstrap prepends this worktree’s `src/` and `tests/src/` PSR-4 paths, preventing an installed Composer copy of the module from shadowing the code under test.
- Kernel tests require `SIMPLETEST_DB`; the repository’s CI uses `mysql://drupal:drupal@127.0.0.1/drupal`, while the documented DDEV command uses `mysql://db:db@db/db`.
- The functional test extends Simple OAuth’s `TokenBearerFunctionalTestBase`, runs each test in a separate process, and requires a reachable Drupal test site through `SIMPLETEST_BASE_URL`; missing database, web server, or base URL is an environment/configuration failure, not a test assertion failure.
- The README’s canonical full-suite invocation is `ddev exec env SIMPLETEST_DB="mysql://db:db@db/db" SIMPLETEST_BASE_URL="https://drupalmcp.ddev.site" vendor/bin/phpunit -c web/modules/custom/drupal_mcp/phpunit.xml.dist`.
- CI deliberately runs only `tests/src/Unit` and `tests/src/Kernel`, despite the repository PHPUnit configuration also discovering the functional suite; reproducing CI and running the complete documented suite are therefore distinct checks.
- CI’s supported test environment is a clean Drupal `recommended-project:^11.4` installation on PHP 8.4 with MySQL 8.0, `pdo_mysql`, `gd`, `drupal/core-dev:^11.4`, and this module installed as a Composer path repository.
- The module’s four Composer patches are part of the executable test environment; CI copies `patches.json` and `patches/`, installs through `cweagans/composer-patches`, and verifies the Simple OAuth user-cache-context patch plus `patches.lock.json` before PHPUnit.
- Validation is separate from PHPUnit in CI: `composer validate --strict --no-check-lock`, YAML parsing, Drupal/DrupalPractice PHPCS over `src` and `tests`, and `composer audit` should be reported separately from test assertion results.
- The README references `scripts/test-mcp-architecture.php`, `scripts/test-mcp-oauth-flow.sh`, `scripts/test-mcp-tools.sh`, and `scripts/test-mcp-denials.sh`, but those files are absent from the supplied project inventory; inability to execute them is a missing-script/repository-state issue, not a failed test.
- Independent-client conformance is a separate live integration harness at `tests/conformance/run.sh`; it requires `curl`, Node/npm, Python, `uv`, a reachable HTTPS MCP endpoint, and either `MCP_ACCESS_TOKEN` or provisioned OAuth credentials.
- Without `MCP_ACCESS_TOKEN`, conformance depends on the local OAuth client/users created by `scripts/mcp-oauth-setup.php` and credentials from `secrets/mcp-test-credentials.txt` (or `MCP_PASSWORD`); provisioning failures must be distinguished from MCP client assertion failures.
- The conformance harness installs pinned TypeScript and Python client packages into temporary/cache locations at runtime, so network/package-install failures are dependency-environment failures rather than module test failures.
- `docs/conformance.md` records prior successful conformance evidence, but that historical result must not be presented as the outcome of the current run.
